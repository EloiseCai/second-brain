# 通用底座与主题补充协议

## 职责与加载

writing-router负责顺序、分支和恢复。每个模块的Skill维护可迁移的方法、思考步骤、输入输出和检查；平台包补充载体要求；主题包按节点提供该账号的人群、素材、表达偏好、产品和品牌资料；本稿Brief记录本次选择。四者组合执行，不为一个产品另写整套平行流程，也不把产品名称、功能清单或案例搬进通用底座。

进入每个节点时，读取对应模块当前Skill、当前平台要求、主题包的节点映射及该节点实际资料。已经完整读取且版本未变的输入可沿用并记录位置，不重复全库调研。主题包缺少映射时先在已绑定账号目录定位；不能因为一份摘要没写就让用户重述已有资料。

漫画产品开启时，story-builder与product-amplify是同一个联合写作节点；下表区分模块职责，不表示先交无产品故事再补产品。第一版必须交完整产品故事，按[主线与节奏协议](../../story-builder/references/story-arc-and-density.md)复核。

## 各节点要完成什么

| 节点 | 通用思考与实际输出 | 主题补充 |
| --- | --- | --- |
| 洞察与选题 | 找到触发时刻、动作、阻碍及原始证据，验证本题可展开性 | 当前账号洞察、关键词、真实记录、研究范围 |
| content-planner＋hook-generator | 每份稿件独立完整Brief、钩子及兑现位置、产品选择 | 账号价值、语言偏好、相应载体的对标与规律 |
| story-builder | 具体事件如何展开困境、行动和变化；明确叙述者及事实归属 | 故事来源、漫画或正文主对标、主题故事方法 |
| product-amplify（on） | 困境→对应能力→具体动作→直接帮助；选承接形式，写出实际产品句和位置 | 产品事实、产品承接规律、相关图库/截图、真实使用记录；各自证据作用分开 |
| content-writer及实际写作模块 | 产出整篇或逐页完整文字，把前述交接落实到正文和分镜 | 当前载体表达、品牌视觉、产品用词、用户已认可句子 |
| critique与交付 | 对实际文字、图片逐项检查，修复断链、漏项和混用，再核对批准范围 | 同一批主题资料与当前写作原则，不临时新增限制 |

产品故事优先使用第一人称“困境—使用动作—具体帮助”；无法形成直接链路时，可先给简单方案，再轻量分享工具，细则引用story-builder的[两种形式](../../story-builder/references/story-development.md)。功能必须回应原问题，不能为迁就已知功能换掉困境。漫画Tone reference来自漫画实际文字；独立文字稿另用自己的正文对标。Forbidden只保留用户明确特殊要求，证据缺口回到事实核对。

## 执行与恢复

各节点在现有制作备注记录：实际输入与版本、使用的主题补充、实际产物位置、发现问题及修改、状态、下一步。状态区分未执行、已读取待产出、待补证、待审批、完成；只有读Skill、读功能表或写了提纲不能标为完成。复核用原文和实际产物，不能仅列调用过的Skill名。

product-amplify的交接至少给出本稿开关、问题与功能匹配、能力依据、承接形式、实际文案、叙述者/使用依据、出现位置与尚缺证据；适用产品图时另有资产方案或实际图。writer接到实际内容后整合，不自行跳过产品模块重新凑一段。

用户纠正流程时，先判断归属：可迁移的方法写回通用模块；产品特有资料和偏好写入主题包及其引用；单篇决定写回本稿。修改后同步运行副本，回读检查，并检查当前稿受影响节点。规则审计本身不自动生成图片或发布，未跑完的分支保持试行。
