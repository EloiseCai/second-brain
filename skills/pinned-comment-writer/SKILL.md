# 置顶评论写作

小红书 content-writer 的 L2 阶段，位于 Hashtag 后、整篇验收前。正文的文末互动问题仍由 body-writer 完成。公众号不自动增加此阶段。用户只要求调研时只建立评论库与分析，不生成或发布评论。

读取 writing-router 的账号配置和当前断点，组合 writing-core、实际平台包及主题包。产品名称、功能、使用入口和真实场景引用当前账号资料；账号未知不默认妈妈善食。评论对标来源读取飞书账号配置 `pinned_comment_benchmarks`，采集与分析执行 [评论对标调研](references/benchmark-research.md)。

## 执行

0. **先读取已确认的评论目标（严格执行）：** 优先采用用户本篇明确要求，其次采用主题包中用户已确认的长期默认值；两者都没有时，询问“本篇是否需要招募内测？”。已有明确回答或长期默认不重复询问，记录其实际来源；不能仅因产品处于早期推定招募。需要内测才写相关邀请，不需要则删除内测、测试名额、共创招募等暗示。账号默认内容由主题包维护，通用模块只引用。

1. 读取本篇最终标题、正文、图片与产品批准范围。明确评论承接本篇哪个需要、希望读者做什么、实际能得到什么。用户未决定的具体转化形式先由研究提出候选，不固定为扣关键词、私信或某种句式。
2. 从本账号已核验评论库选择匹配目标的主对标，完整读取原评论及必要上下文、评论自身互动证据、已存逐句分析。必须同时满足作者本人发表、可见置顶标识、评论含产品触达引导／内测招募／进群引导及评论自身互动证据。普通回复不作为本库可用对标或规律证据；仅有功能介绍、闲聊、教程更新、上线状态而无触达信息的评论排除。先读取 pattern-extractor 在本账号提取的评论引流规律，再回到合格原文逐句写作。缺样本定向补查，不重跑已完成选题调研。
3. 先列源评论每一句/独立语义单元的功能与衔接，再写本篇对应句。记录“源句ID→功能与语气→本篇事实及依据→成稿句→改动理由”。覆盖全部单元；不能只挂来源名或先写广告再套对标。原评论只有一句时按完整语义分析，不机械按换行切碎。不照抄原作者个人经历或专属事实。
4. 每句执行通用、平台、主题 critique：是否清楚有信息、是否能更简洁有力、读者是否知道下一步；再检查与正文承诺相接、产品功能属实、动作真实可执行、表达及渠道符合当前账号规则；逐字检查主题包禁用词，妈妈善食引用pregnabite-writing的产品承接用词与置顶评论默认承接要求。原帖有违规或不可复用动作仍如实存研究，成稿按实际规则改写，不用暗号绕过。
5. 修改复查后在同一飞书稿独立区块交付“建议置顶评论”，与可复制发布正文/Hashtag 分开；源句对应和 critique 留制作备注。产品新增说法待用户复核，不因评论来源有此功能就替本账号批准。整篇验收必须核对本区块；未通过保持 L2。

## 长度与笔记关联（严格执行）

轻量置顶评论默认30—60字，按去除空格与换行后的Unicode字符数统计，标点、数字、字母及Emoji编码字符计入；这是本项目写作配置，不是平台字数上限或对标平均值。交付前实际计数并在制作备注记录。只保留一个与笔记直接相关的产品用途、一处邀请及一个主要参与动作；主题包已明确要求加群邀请与可选内测回复并列时，保留两项并分清意愿，不额外增加动作。可选问题不得挤长文本。内测版保留明确内测邀请，早期状态按本篇或主题包要求处理且须属实，优先删功能堆叠和重复打磨语句。必要报名条件无法容纳时先提出超长理由与候选，交用户选择，不静默越界、不删关键条件凑字。

评论须承接本篇实际内容：写前记录“本篇讲什么→评论选哪个相关用途→希望读者做什么”。食谱笔记可承接食谱生成，家人做饭可承接分享，备菜可承接食材清单；这些只是依据已确认功能的例子，不强制一篇列全。共用产品名与邀请骨架，相关用途随笔记调整；没有直接关系就说明缺口，不能硬塞产品、不编造困扰、不声称对标账号每篇都留同一评论。

断点记录本篇是否招募内测及用户回答、主评论样本、已读分析版本、当前草稿与实际字数、笔记关联、逐句检查及产品批准状态、下一动作。写好草稿不代表已发布或已置顶；发出和置顶需用户明确授权。
