# 真实用户洞察报告

## 核心原则

先用六维选项池组合出问题假设，并用搜索等真实材料发现新问题、验证和修正假设。允许推演作为调研出发点，必须标明假设；不能把推演当真实痛点，也不能只挑支持材料。新调研主动检索；已采素材的需求回写执行下述增量模式。

## 对标需求回写（严格执行）

接收 pattern-extractor “对标分析”产出的需求卡，先读取其 [核心需求提取规则](../pattern-extractor/references/benchmark-analysis.md#核心需求提取严格执行)，核对对象、具体缺口、希望得到的答案和原文依据。提取方法与来源性质由该文件唯一维护，本 Skill 负责问题库去重、整合与回读。

此模式整合已有证据，不重新启动五路调研或生成一批六维假设。按 [问题库 SOP](references/problem-library-sop.md) 读取现有《用户洞察》全文，以任务、触发场景和实质障碍去重；同一问题补证或补角度，新任务才建问题ID。

问题卡保留必要原话、具体问号、证据增量及原素材链接，完整写法分析与知识依据由原文档唯一维护。更新问题索引、相关卡片和来源记录，写后回读，再将问题ID与链接交还原素材。只有完成实际回写才称需求已入库；后续全库处理按用户授权批次执行。

回写及存量修正必须执行 [来源到问题卡的逐条验收](references/problem-library-sop.md#41-来源到问题卡的逐条验收严格执行)，并引用 [具体角度保留规则](../writing-core/references/angle-fidelity.md)。上层分类用于检索；交给选题的仍是带来源的具体处境、对象和问号。每条记录验收通过后才能入库；一项不通过就修正该条及受影响的汇总、方案和原素材关联，再回读复查，不以整批概括评价代替逐条检查。

PregnaBite 用户于2026-09-24确认：研究以孕妈人群为起点，覆盖她们的各类具体问题，不限于食谱、补剂或现有产品功能。先发现问题与当下情绪，再匹配解决方案；新功能可先通过内容验证需求，再决定开发。旧定位与固定词表中的营养范围作为已有业务背景，不再作为本账号需求发现的排除条件。其他账号沿用各自范围。研究孕期医疗、职场或家庭问题不等于可以编造诊断、法律建议或产品能力；解答需另行核验。

## 每轮主动调研与交接

每次新选题调研必须先执行 [六维组合、人群问题库与验证 SOP](references/problem-library-sop.md)，再按 [多渠道调研与六维洞察](references/research-workflow.md) 取证：列举六维选项 → 兼容组合生成问题假设 ↔ 搜索、数据平台、笔记、反馈及同类产品五路调研 → 定义并合并问题ID → 比较方案 → 内容验证 → 按问题/角度/方案聚合数据回填。主交付始终是用户的具体问题、困惑与当下情绪；关键词指数辅助发现方向及后续埋词，不能取代问题卡。六维必须参与前期生成，不能只作为事后记录字段。只更新规则或局部改字不触发整轮研究。

- 全人群研究先横向发现问题；用户指定某个问题时在该范围内执行相同渠道检查。已完成的同轮证据包可以被多篇复用，每篇核对适配性并补查缺口，不机械重复采集。
- 每条渠道记录已完成、部分完成或不可访问及具体原因。付费、登录缺口不能用AI生成热词、指数或评论填充；如有缺口，交付明确标注“部分调研”，不称完整完成。
- 评论与求助可以在本阶段发现主问题，跨来源核对后再形成候选；选题已确认后的写作阶段，评论继续用于补充与验证，不让孤立评论任意改写主线。
- 交接给 topic-generator 的是问题卡、原始证据、情绪依据、已有解法缺口、多个实质不同的 angle 和解决方案状态；先研究问题，再用对标研究怎样表达。不因产品尚无功能淘汰有依据的问题。

可使用的素材包括：

- 小红书搜索联想；
- 已实际读取的官方或第三方数据平台报表；
- 真实笔记及其评论区；
- 用户反馈；
- App 内的真实搜索词或输入内容；
- 同类孕妈 App 和小程序的功能、使用评价与可定位的用户追问；
- 用户访谈；
- 有记录依据的产品观察。

搜索联想和产品观察可以提供线索，但不能单独证明需求频率、普遍程度或重要性。不要把博主概括、产品团队判断或 AI 推断冒充用户原话。

## Step 1：六维生成与真实用户素材库

研究先交付维度选项及组合假设，再交付“具体困惑与切入角度库”，再写痛点、桥梁或整体分析。一个可进入已确认角度库的素材，应尽量同时回答：用户在什么时刻或处境、面对什么具体对象/任务/选择、想完成什么、矛盾或顾虑是什么、最后卡在哪个问号。像“孕期营养很重要”“孕妈不知道吃什么”只能作为上层归纳，不能排在具体素材之前，也不能单独成为 angle。

1. 确认本次报告对应的账号、人群、产品和分析范围。不同账号、产品或人群的素材分开处理。
2. 盘点用户已提供或已授权读取的素材库。只读取与本次范围直接相关的内容；原文不可访问时记录缺口，不根据标题、互动数或摘要补写内容。
3. 保留具体的原话和上下文。优先选择能说明“谁在什么情况下，遇到什么选择或阻碍”的表达，例如：“孕吐但是空腹更想吐，不知道早餐吃什么。”
4. 为每条素材记录来源类型、来源名称或文件路径、直接链接或可定位标识、日期（可见时）、采集日期、原话、必要上下文，以及是否来自用户本人。
5. 将原始证据与 AI 归纳分开。先保存原话，再忠实归纳具体场景、想完成的事、卡点、已经尝试的办法和仍未解决的问题；原文没有的信息留空。
6. 按“同一人群在同一场景下面临的同一问题”合并近义材料。保留各自来源和不同细节，不把多个来源拼成一个虚构人物或经历。
7. 标记材料状态：可直接使用、需要补上下文、仅作线索或与当前范围无关。没有可追溯证据的痛点不进入已确认素材库。
8. 按“对标需求回写”区分作者自述、内容推断和团队创作场景。作者对本人处境与尝试的具体表达可直接作为具名需求证据；内容反推与创作场景保留推断性质，并继续补实际表达。
9. 把每条可用素材改写成一个忠实于原意的具体问号，并保留原话。问号应落到当下选择，例如“想补叶酸但不想天天吃菠菜，还能换哪些家常菜”，不能只改成“用户需要多样化营养方案”。

每条有效素材至少包含：

- `用户原话`：短摘录，保持原意；
- `具体场景`：人群、处境和眼前的选择，只写证据支持的细节；
- `真实卡点`：用户想完成什么、卡在哪里；
- `六维问题卡`：生活场景、人群身份、孕周阶段、核心痛点、当下情绪、行动障碍；情绪原话与AI解释分开，未知留空；
- `来源`：素材类型、具体路径或链接、可定位信息；
- `证据性质`：直接求助、实际搜索/输入、访谈反馈、经验描述、博主概括或产品观察；
- `AI 归纳`：与原话分栏，并标明这是分析；
- `材料状态`：可用、待补上下文、仅作线索或不采用，并说明理由。

## 判断质量

优先保留带具体情境、矛盾和待解决选择的表达。像“孕早期营养摄入非常重要”这样的泛化陈述不能当作真实痛点，除非它有明确来源且上下文说明了用户实际遇到的问题。

不要从少量素材推断“多数用户”“最近都在讨论”“高频刚需”或市场规模。互动量、重复出现次数和搜索联想只能作为本次样本内的观察，记录样本范围后再描述。

如果素材不足，输出已有证据、缺失项和建议补采的来源或问题。不要用常识、想象案例或虚构访谈填满报告。

## 交付

先展示本轮六维选项池增量、组合假设、问题ID索引与待用户审核项，再按以下顺序交付：

1. `具体困惑与切入角度库`：先列用户原话、具体处境、眼前矛盾、忠实改写的具体问号、来源和证据状态；
2. `待验证角度`：收纳由内容反推、产品观察或创作推演得到的具体场景，并写清还缺什么证据；作者本人具体经历按直接表达归入对应问题；
3. `受众洞察与解决方案`：只从前两部分向上归纳，记录现有解法与缺口、内容能先交付的答案、已上线功能/待核实能力/新功能假设/无需产品的解决方案，已确认与待验证结论分开；
4. `样本范围与补采计划`：列出访问缺口、未采用材料及原因，以及下一步应去哪些评论区、搜索词、App 输入或访谈问题补采。

报告中标为已有直接表达或交叉支持的痛点都要能回到具体素材；六维组合假设可以先入待验证区，保留组合依据与补证计划，不能冒充真实表达；引用原话与分析结论清楚分开。用户明确提供的本人真实困惑可以入库，但不得据此推断它能代表更多用户，必须继续寻找近义评论、搜索或行为证据。

每次执行前先用 user 身份读取固定文档的当前可见全文，再将新素材和洞察整合进已有结构。相同用户情境和痛点原位补充证据与分析，不重复创建近义条目；新主题才新增洞察章节。保留已有有效内容、来源编号和证据状态，不在文末无序追加。

《用户洞察》只维护一个“关键词搜索”分区和一张持续更新的关键词表。每行写平台实际检索到的词或紧凑短词组、父词、指数展示量级、来源和关联问题；完整问句只进入问题卡。按平台原始指数全表降序排列，每次加入新词或更新指数后都重新排序全表，插入其正确位置，不在表尾追加；万级显示一位小数的“万”，千级显示一位小数的“K”，不足千约到百位，原值留在取数记录用于排序和更新。词表开头写明两个用途：比较选题角度的搜索信号，以及为与内容相符的笔记选择自然埋入的高指数词。更新时合并到现有行，不按取数日期新建拓词章节或保留过时过程稿。整篇文档以当前问题、证据、方案和回填为主线，旧批次中仍有效的信息融入相应位置。

六维选项池、具体任务场景和组合示例是《用户洞察》的固定人群研究内容。整理文档时必须保留并原位更新，不能为了缩短文档把这些内容移走或删除；需说明场景、身份、阶段如何限定问题，痛点和障碍如何确定卡点，情绪如何由真实表达核对。新增六维项先查已有选项与问题ID，重复项补证，实质不同才扩库。

不要为每次报告创建新文档，也不要另存成本地 Markdown 代替飞书记录。只有固定文档已删除或无法恢复，并且用户明确要求重建时，才在上述父节点下创建替代文档并同步更新这里的 token。

写入后回读固定文档，核对标题、素材记录、来源、AI 归纳、样本范围和访问缺口均已保存。只有更新与回读验证成功后才称为已入库，并向用户返回固定文档链接；如果写入失败，保留已经完成的报告内容并明确说明阻塞原因，不声称已经记录到飞书。
